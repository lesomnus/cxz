# 대화 저장소: 세션이 자기 대화를 쓴다

상태: 제안. cxz#238. 구현은 이 문서가 합의된 뒤에.

목표는 하나다. **대화의 내구 저장소를 세션당 하나로 만들고, 그것을 쓰는 프로세스를 그
세션의 수퍼바이저 하나로 둔다.** 그러면 프로세스가 새로 뜰 때마다 저장소 둘을 맞추는
일이 사라지고, 매니저가 들고 있는 두 번째 사본도 사라진다.

## 지금의 지도

프로젝트 컨테이너 안에서 실제로 돌고 있는 것들이다.

```
cxz --state /cxz/state/data _project              서버.       프로젝트당 1개
cxz --state /cxz/state/data _supervise <session>  수퍼바이저.  세션당 1개
└─ codex app-server | claude                      에이전트.   수퍼바이저의 자식
   └─ cxz … _mcp-bridge <session> <name>
```

| | 수퍼바이저 (세션당) | 서버 (프로젝트당) |
|---|---|---|
| 쓰기 | 자기 세션의 `events.jsonl` | `cxz.db`: `events` 캐시, `transcript_*`, `sessions` |
| 읽기 | 자기 저널 | 모든 세션의 저널 |
| DB | 접근하지 않는다 (패키지에 참조가 없다) | `daemon.lock`을 잡은 단독 writer |
| 소켓 | 세션별 소켓 (`update-status`/`activity`/`stop`) | 프로젝트 gRPC 소켓 |

저장소마다 writer는 하나다. 저널은 세션별 파일이라서, DB는 `core.Lock(root/daemon.lock)`
이라서 그렇다. 나머지는 모두 읽기다 — `versionuse`는 `mode=ro`로 열고, 버전 전환 경로는
같은 `daemon.lock`을 잡아 서버가 없을 때만 진행한다. `conversations.db`(검색)와
`auxiliary`는 애초에 별도 파일이며, 그 이유가 `internal/convindex/index.go`에 적혀 있다:
단일 커넥션 뒤에 검색이 줄을 서지 않게 하려고.

## 버전 번호들

지금 코드에 있는 것들이고, 중요한 것은 번호가 아니라 **불일치할 때의 동작**이다. 문서는
없었다 — 이 절이 그것이다. 1단계가 들어가면 `docs/development.md`로 옮긴다.

| 버전 | 현재 | 어디에 | 불일치하면 |
|---|---|---|---|
| `PRAGMA user_version` (cxz.db) | 2 | DB 헤더 | **거부.** `server.Run`이 `> 2`면 시작하지 않음 |
| `transcripthistory.projectionFormat` | 5 | 세션별 `transcript_format` | **재구축.** 이벤트에서 다시 만듦 |
| `cxzupdate.Protocol` | 1 | 빌드에 박힘 | **구동 거부.** 거절 문자열의 `(protocol 1)` |
| `cxzupdate.Schema` (= `releasechannel.StateSchema`) | 2 | 릴리스 매니페스트 | 롤아웃이 후보 거부 (`candidate identity mismatch`) |
| `core.HistoryCheckpoint.Version` | 1 | 체크포인트 payload | **디코드 거부** |
| ent/payday 마이그레이션 | — | resources.db | 마이그레이트 |

규칙이 하나 나온다. **내구적인 것은 거부하고, 파생된 것은 재구축한다.**

`user_version`은 스키마 버전이 **아니다**. `MarkHistoryTrimmable`의 주석이 말하는 대로
롤백 울타리다 — `1`은 아직 트림한 적 없음, `2`는 구멍이 있을 수 있음이고, 트리밍을 모르는
릴리스는 사라진 대화를 서비스하는 대신 거부한다. `versionuse.validateDatabase`가 버전
전환 전에 읽는다. 그래서 `1`은 레거시가 아니라 상태 하나이며 폐기 대상이 아니다.

라이브 설치본의 실제 값이다.

```
프로젝트 런타임 /cxz/state/data/cxz.db
  user_version = 2    transcript_format: 5×4 세션    워터마크 4/4

매니저 /var/lib/cxz/cxz.db
  user_version = 2    transcript_format: 5×14, 4×1, 3×1, 2×1
                      워터마크 14/17  ← 없는 3개가 정확히 포맷 2·3·4인 그 3개
```

포맷 2·3·4 행이 남아 있는 것은 그 세션을 아무도 열지 않았기 때문이고, 다음 접근에
사라진다. 과거 포맷 행을 **읽는** 코드는 없다 — 폐기할 코드가 없다는 뜻이고, 재구축
정책이 옳다는 실증이기도 하다. 낡은 파생이 아무 해도 끼치지 않고 남아 있었다.

## 무엇이 문제인가

내구 저장소가 **둘**이다. 저널과, 그것을 복사한 `cxz.db`의 `events`. 그래서 서버가 새로
뜨면 세션마다 저널을 처음부터 읽어 (a) 살아있는 스냅샷을 리플레이하고 (b) 캐시의 꼬리가
저널과 일치하는지 확인한다. `cxz` 프로젝트를 recreate한 직후 측정했다.

```
세션당 첫 접근 (디스크 캐시 따뜻한 상태, 라이브 DB 스냅샷 대상)
  4d683e9c  82MB/ 78,339  lockProjection 603ms  sync 153ms  page  39ms
  d57f2e00  85MB/122,236  lockProjection 946ms  sync 158ms  page 102ms
  9b3bc6ba  72MB/103,498  lockProjection 539ms  sync   0ms  page 104ms
  c99d1b14  47MB/ 32,904  lockProjection 260ms  sync   1ms  page  60ms

저널 읽기와 리플레이만 따로 재면
  read 453ms / replay 11ms,  413/6,  203/1,  529/19
```

비용은 거의 전부 읽기와 파싱이다. 리플레이는 6~19ms다. 그리고 그 작업은 세션별 projection
락을 쥐고 일어나므로, 같은 세션에 오는 다른 호출이 뒤에 선다. 라이브 로그가 그 모양이다.

```
Transcript        OK  3635ms  waited_ms=0     ← 락을 쥔 쪽
Background        OK  3072ms  waited_ms=3001  ← 뒤에서 대기
GetHistoryFloor  ×4  2000ms  Unknown         ← 2초 데드라인에 실패
List             ×2  ~2000ms Unknown
```

사용자에게는 "대화 불러오기가 느리다"로 보인다. 이것은 cxz#227에서 고친 두 가지와 성질이
다르다. 그 둘(버릴 본문을 읽던 metadata 쿼리 0.3~2.0초, 재시작마다의 체크포인트 재기록
3.98초)은 **버그**였고 고쳐졌다 — 지금 `Page`는 1~2ms, 재조정 없는 sync는 82ms다. 남은
이것은 **구조**다. 저장소가 둘이라서 생긴다.

매니저 쪽에 같은 중복이 한 겹 더 있다. 매니저는 프로젝트 컨테이너의 볼륨을 읽을 수 없으니
대화를 자기 `cxz.db`로 복사해 둔다 — `m.cache`, `down` 직전의 capture("history survives
the container"), 런타임이 답하지 않을 때의 폴백("remains readable offline"). 그 복사본
때문에 매니저 DB가 845MB다. 복사가 있는 이유는 정당하다: `project down`은 컨테이너만
지우고 데이터를 남기고, 지금 `xli`가 `absent` 상태로 그렇게 있다. 컨테이너가 없어도 대화는
읽혀야 한다.

## 설계

### 세션당 대화 DB 하나, writer는 그 세션의 수퍼바이저

```
sessions/<id>/conversation.db     세션당 1개. writer는 그 세션의 수퍼바이저 하나.
  PRAGMA user_version = 1         스키마 모양. 단조 증가.
  meta.compat        = 1          이 DB에 써도 되는 가장 낮은 코드 세대
  meta.rows_format   = 5          파생 해석 버전. projectionFormat을 그대로 이어받는다
  meta.trimmed       = 0|1        오늘 user_version=2가 뜻했던 능력 울타리
  events                          provider가 말한 것. 내구적.
  rows, records                   표시용 리덕션. append와 같은 트랜잭션.
  snapshot                        리덕션 상태 1행. 재시작이 이것을 읽는다.
```

번호를 이렇게 정한 이유는 둘이다. 오늘 `user_version`은 **스키마 모양과 트림 능력을 한
숫자에 섞어** 놓았고, 그것을 분리한다. 그리고 `rows_format`은 새 번호를 만들지 않고 5를
이어받는다 — 해석 규칙이 바뀌지 않으므로 변환기가 만드는 행은 지금 코드가 읽는 행과 같고,
새 번호를 붙이면 "5와 1이 같은 모양"이라는 설명이 영구히 따라붙는다. 세션당 DB가 하나이니
`transcript_format` 테이블은 사라지고 행 하나가 그 자리를 대신한다.

`rows`와 `records`는 같은 DB에 둔다. writer가 하나이므로 쓰기 락을 공유할 상대가 없다.

수퍼바이저는 이미 리덕션을 하고 있다 — `snap`(state·run id·vendor id·last seq),
`pending`, `updateTools`, `updateBackground`를 append하는 자리에서 유지한다. 표시용 행
리덕션(`transcripthistory.Projection.Apply` + `summary()`)은 서버에 의존하지 않는 순수
함수이며, 이미 서버 밖에서 돌고 있다: WASM 샌드박스가 `memory.go`의 `FromEvents`로 같은
리덕션을 한다. 옮기는 것은 호출 주체다.

그러면 이렇게 된다.

- **재조정이 없다.** 복사할 것이 없고 행이 이미 거기 있다. 위의 0.3~1.2초가 0이 된다.
- **재시작이 리플레이가 아니다.** 스냅샷 한 행을 읽는다. 이 메커니즘은 이미 있다 —
  압축이 쓰는 `core.HistoryCheckpoint`가 `Snapshot`을 품고 `ReplayFrom`이 거기서 리셋한다.
  이 설계는 그것을 압축 때만이 아니라 평상시 경로로 만든다.
- **writer가 파일당 하나로 유지된다.** fork는 파일 복사, 압축은 행 삭제, purge는 unlink다.
  오늘 파일이 주던 격리가 그대로다.
- **서버와 매니저는 읽기만 한다.**

### 왜 리덕션을 버리지 않는가

"진실 하나만 읽자"가 자연스러운 질문이고, 답은 리덕션이 사본이 아니라 **해석**이기
때문이다. 행 하나가 이벤트 여럿의 축약이고, 나중 이벤트가 앞선 행을 고친다.

- 툴 호출 하나가 `tool_call` → `tool_output` → `tool_result` → `approval` →
  `approval_resolved`로 도착해 **행 하나**로 접힌다(`pending`→`working`→`completed`/`failed`).
- `turn_end`은 자기보다 **앞선** assistant 행에 토큰·비용·소요시간을 접어 붙인다. 둘은
  수천 이벤트 떨어져 있을 수 있다.
- `raw`·`state`·`vendor`·`usage` 같은 kind는 행을 만들지 않는다.
- 페이지가 작으려면 payload를 떼야 한다. 원문은 `EventDetails`로 필요할 때만.
- `updated` 열이 행 버전 스트림을 가능하게 한다. 정정이 뒤에 도착하고 읽는 쪽이 seq로
  교체한다.

그래서 매 페이지마다 리덕션을 다시 하려면 **얼마나 거슬러 올라가야 하는지 알 수 없는**
역방향 스캔을 해야 한다. 그 비용의 실측이 cxz#227에 있다: 1.6만~2.6만 레코드를 훑던
쿼리가 0.3~2.0초였다.

반대로 리덕션을 내구 저장소로 삼으면 — 행만 남기면 — **리덕션 버그가 영구 데이터
손실**이 된다. `projectionFormat`이 이미 5인 것이 해석이 네 번 바뀌었다는 뜻이다. 지금은
`toolview`를 고치고 다시 만들면 되지만, 행만 남기면 과거 대화가 틀린 모양으로 영원히
남는다. `EventDetails`의 원문 보기, fork, resume(vendor id·`checkpoint.Resume`)도 이벤트가
있어야 성립한다.

결론: **이벤트는 내구적으로 남고, 리덕션은 그 옆에 같은 트랜잭션으로 저장된다.** 파생이
사라지는 것이 아니라, 파생을 만드는 주체가 소유자와 같아지고 저장소가 하나가 된다.

세션을 넘는 파생만 따로 남는다 — 검색 색인(`conversations.db`)과 리소스 저장소
(`resources.db`). 세션 DB 안에 둘 수 없는 것들이고, 검색 색인이 파생인 것은 어느
설계에서도 그렇다.

### 검색 색인: 커서는 이미 있다, 트리거만 바뀐다

`convindex`의 스키마가 이미 커서 기반이다.

```sql
CREATE TABLE IF NOT EXISTS sessions(
  ...
  -- Events through here are ingested, with no gap behind them. A gap is ...
  cursor_seq INTEGER NOT NULL DEFAULT 0,
  ...
)
```

`Ingest(ctx, s, events, from, through)`가 구간을 명시적으로 받고, 커서보다 뒤에서 시작하는
구간은 틈을 남기므로 행은 보관하되 커서를 전진시키지 않는다. 즉 커서와 틈 감지가 다 있다.
바뀌어야 하는 것은 **호출 지점 하나**다. 지금은 매니저가 캐시에 배치를 커밋한 직후
`extractConversation`이 밀어넣는다(push). 캐시가 사라지면 당길 주체가 필요하다.

색인은 매니저에 하나로 둔다 — 검색이 한 번의 쿼리로 끝나야 하고, `convindex`의 주석도
"사람이 검색하는 양은 작다"를 전제한다. 3단계 이후 매니저는 세션 DB를 읽을 수 있으므로:

```
세션마다:  SELECT MAX(seq) FROM events      ← 색인 하나, cxz#213에서 이 모양을 0.005ms로 측정
           cursor_seq와 같으면 끝
           다르면 접미부만 읽어 Ingest(from=cursor+1, through=max)
```

- **크래시 안전**: 색인 행 삽입과 커서 전진을 색인 DB의 한 트랜잭션에. 죽으면 같은 구간을
  다시 읽고, `(session, seq)` upsert라 멱등이다.
- **트림**: 세션의 첫 seq가 커서보다 위로 올라가면 사라진 것을 색인에서 지운다. 스키마에
  `trimmed` 열이 이미 있고, `transcripthistory.Sync`의 양 끝점 비교를 그대로 쓴다.
- **트리거**: 세션이 바뀌었다는 것을 매니저가 이미 알고 있으니 그때 그 세션만 훑고, 30초
  타이머가 바닥이다. 전수 폴링은 하지 않는다.
- **지연**: 지금 코드가 이미 "파생 저장소가 뒤처지는 것은 그것이 서비스하는 검색이
  보고한다"고 선언한다. push에서 pull로 바뀌면 지연이 트리거 간격 모양이 된다.

### 규칙

**내구성.** 지금 `AppendBatch`는 배치마다 `l.f.Sync()`를 호출한다. 같은 보장을 유지하려면
WAL + `synchronous=FULL`로 커밋당 fsync다. 비용은 오늘과 같다(배치 단위).
`convindex`가 `NORMAL`인 것은 파생 데이터라서이며, 대화에는 쓰지 않는다.

**리덕션 실패가 append를 막지 않는다.** 지금은 이상한 payload에 리덕션이 넘어지면 *보기*가
깨지지만, 쓰기 경로로 들어오면 *기록*이 막힐 수 있다. provider가 예상 밖의 것을 보내는
일은 실제로 일어난다 — cxz#235의 `codex-code-mode-host`가 그런 식으로 왔다. 그래서:

> 이벤트를 먼저 커밋한다. 행은 같은 트랜잭션에서 최선으로 쓰되, 리덕션이 실패하면 그
> 세션에 "행 재구축 필요" 표시를 남기고 이벤트는 그대로 둔다.

**포맷 버전과 과거 행.** 재구축 주체는 그 세션의 수퍼바이저인데, 멈춘 세션에는
수퍼바이저가 없다. 지금 설치본의 세션 23개 중 13개가 `stopped`이므로 가정이 아니다.
선택지는 셋이고, 선호는 첫 번째다.

1. **읽는 쪽이 기록된 포맷 그대로 읽는다.** 행에 버전이 적혀 있으면 읽는 쪽이 "이건 v4
   행이다"를 알고 다룬다. 멈춘 대화는 더 이상 바뀌지 않으니 재구축이 필요 없다 —
   재구축 자체가 줄어든다.
2. 세션이 다음에 시작될 때 재구축한다. 멈춘 채로는 옛 모양으로 남는다.
3. 서버가 멈춘 세션에 한해 재구축한다. writer 하나 규칙에 예외를 만든다.

**스키마 스큐.** 세션 DB를 쓰는 것은 자기 수퍼바이저 하나뿐이므로, 필요한 것은 버전 열과
"내가 모르는 스키마면 쓰지 않는다"다 — 서버가 `user_version`에 적용하는 규칙과 같다.
수퍼바이저를 서버와 lockstep으로 올리는 방법도 있지만 공짜가 아니다. 업데이트가 계단식인
것은 턴 중인 세션을 끊지 않기 위해서이고, lockstep은 "프로젝트 런타임이 올라갈 때 세션
재시작" 또는 "모든 세션이 조용해질 때까지 서버 대기" 중 하나를 강요한다. 후자가 cxz#224와
cxz#235에서 업데이트를 멈춰 세운 그 게이트다.

## 2단계: 프로젝트별 볼륨 → 매니저 볼륨의 서브패스

매니저 캐시를 없애려면 매니저가 세션 DB를 직접 읽어야 한다. 처음에는 호스트 디렉터리를
매니저에 바인드하는 안으로 적었지만, **더 좋은 방법이 이미 레포에 있다.** 지금 relay와 web
컨테이너가 매니저 볼륨을 서브패스로 마운트한다.

```go
// internal/installer/relay.go
"--mount", "type=volume,source=" + v.StateVolume + ",target=/var/lib/cxz/run,volume-subpath=run,readonly"
```

그래서 프로젝트 상태도 같은 방식으로 둔다.

```
지금:  volume cxz-<owner>-<projectID>-state       →  /cxz/state
바꿈:  volume cxz-<owner>-state, subpath=projects/<id>/state  →  /cxz/state
```

매니저는 자기 루트에서 `projects/<id>/state/`로 같은 파일을 보고, `compose-go`의
`ServiceVolumeVolume.Subpath`가 이것을 표현한다. 호스트 디렉터리 안과 비교하면 포기할 것이
사라진다.

| | 호스트 디렉터리 | 서브패스 |
|---|---|---|
| 매니저가 직접 읽기 | 가능 | 가능 |
| SQLite 락 | 호스트 FS를 전제해야 한다 | **named volume 그대로**, 엔진의 네이티브 FS |
| uid/권한 | 호스트 uid 매핑을 설계해야 한다 | 지금과 같다 |
| 호스트 경로 결정 | 필요하다 | 필요 없다 |
| 메커니즘 | 새로 들인다 | 이미 쓰고 있다 |

**매니저는 읽기만 한다.** 쓰기까지 열면 롤아웃 중에 서로 다른 세대의 두 바이너리가 한 DB에
쓴다 — 실제로 매니저가 `5bd4c0c`, 수퍼바이저가 `6f7ea45`인 순간이 있었다.

## 마이그레이션

두 단계의 마이그레이션은 성질이 다르다.

**2단계(볼륨 → 서브패스)는 바이트 복사다.** 데이터 모양이 바뀌지 않으므로, recreate가 컨테이너를
지운 뒤 — 아무도 그 볼륨에 쓰지 않는 유일한 순간 — 볼륨 내용을 매니저 볼륨의
`projects/<id>/state/`로 복사한다. 복사는 **검증한 뒤에** 볼륨을 놓는다: 두 트리의 모든 파일을
이름과 크기로 비교하고, 일치할 때만 프로젝트가 볼륨 참조를 버리고 그 다음에 볼륨을 지운다.
`cp -a`가 0으로 끝난 것은 검증이 아니다. 실패하면 볼륨은 그대로이고 프로젝트는 예전 모양으로
recreate된다 — 데이터가 움직이지 않았으므로 복구할 것이 없다.

export/import 왕복으로 하면 저널 바이트·seq·run id·첨부 하드링크를 재구성해야 하고,
조금이라도 빠뜨리면 그것이 히스토리 손실이다.

**1단계(저널 → 행)는 일회성 변환기다.** 수퍼바이저가 시작할 때 자기 세션의 `events.jsonl`을
읽어 `conversation.db`에 넣고, 끝나면 저널을 보존 모드로 남긴다(지우지 않는다). 변환이
끝난 세션은 DB를 진실로 읽고, 저널은 한동안 그대로 둬서 비교·복구에 쓴다.

범용 export/import는 **향후 기능**으로 둔다. 지금 cxz에서 대화를 밖으로 꺼내는 방법이
없다는 것은 그 자체로 메울 구멍이지만, 이 변경의 전제조건은 아니다.

변환한 뒤에도 **저널 쓰기를 멈추지 않는다.** 1단계부터 4단계까지 저널이 진실이고 세션 DB는
파생이다. 5단계에서 역할이 바뀐다.

처음에는 "한 번 변환하고 전환한다"로 적었는데 그것은 **롤백과 충돌한다.** `cxz use`나 롤백된
매니저 트랜잭션이 옛 수퍼바이저를 되돌려 놓으면, 그 수퍼바이저는 얼어붙은 저널을 읽고
그 뒤로 append한다 — 전환 후 DB에만 기록된 구간이 조용히 사라지고 두 저장소가 갈린다.

대신 역할로 비용을 줄인다. **1~4단계에서 세션 DB는 파생이므로 `synchronous=NORMAL`이면
충분하다**(`convindex`가 파생이라 NORMAL인 것과 같은 이유). fsync는 저널의 것 하나로
유지되고, DB가 깨지면 저널에서 다시 만든다. 5단계에서 저널 쓰기를 멈출 때 `FULL`로
올리고, 그때부터 DB가 진실이다.

### 앞으로 버전이 바뀌면

| 대상 | 불일치하면 | 누가 |
|---|---|---|
| `user_version` (내구 스키마) | 마이그레이트. 모르는 상위 버전이면 쓰기 거부 | 소유자 = 그 세션의 수퍼바이저, 시작 시, 한 트랜잭션 |
| `rows_format` (파생 해석) | 재구축. 지연 가능하며 append를 막지 않는다 | 같은 소유자 |
| `compat` (롤백 울타리) | 내 세대 < compat이면 쓰기 거부하고 그 사실을 보고 | 쓰려는 모든 주체 |

읽는 쪽은 마이그레이트하지 않고, 읽기를 거부하지도 않는다. 모르는 상위 버전이면 아는 만큼
읽고 "더 새로운 cxz가 기록한 대화"라고 말한다 — `session-history.ts`에 반대 방향의 같은
문구가 이미 있다.

**핵심은 롤백이다.** `cxz use`와 롤백된 매니저 트랜잭션은 둘 다 옛 바이너리를 되돌려
놓는다. 새 수퍼바이저가 마이그레이트한 뒤 롤백되면 옛 수퍼바이저가 쓰지 못하고, 그러면
세션이 기록을 못 한다. 그래서 두 가지를 규칙으로 둔다.

1. **DDL은 가산만.** 열과 테이블을 더하기만 하고 뜻을 바꾸지 않는다. 열을 지우는 것은
   롤백 창이 지난 다음 릴리스에서.
2. **가산 변경에서는 `compat`을 올리지 않는다.** 옛 바이너리가 상위 `user_version`을 봐도
   `compat`이 자기 세대 이하면 계속 쓴다. 뜻이 바뀌는 변경에서만 올리고, 그때는 롤백이
   의도적으로 막힌다.

1단계 동안 저널이 남아 있으므로, 마이그레이션이 실패하면 저널에서 다시 만들 수 있다.
그것이 안전망이고, 저널 쓰기 중단이 맨 뒤인 이유다.

## 버리는 것과 대체 수단

저널이 공짜로 주던 다섯 가지다.

| 저널이 주던 것 | 대체 |
|---|---|
| 서버와 무관한 쓰기 내구성 | 유지된다. 수퍼바이저가 자기 DB에 직접 쓴다 |
| fork = 접두부를 읽어 다시 쓰기 | 행 복사 + `session_id` 치환. 지금도 단순 복사가 아니라 `SessionID`를 바꾸고 vendor 식별자를 비운다 |
| 압축 = 파일 재작성 | 행 삭제 + `VACUUM`, 체크포인트는 `snapshot` 행 |
| 찢어진 꼬리를 노출하지 않음 | 트랜잭션 |
| 파일 변경이 곧 신호(`observeJournals`) | WAL 감시 또는 기존 폴링(cxz#213 이후 0.005ms) |
| 스키마 없음 → 버전 스큐 무해 | **대체 없음.** 버전 열 + "모르면 쓰지 않는다"가 비용이다 |

마지막 줄이 이 설계가 새로 들이는 유일한 불변식이다.

## 단계

1. 세션당 `conversation.db`와 변환기. 수퍼바이저가 쓰고, 서버는 그것을 읽어 지금의
   `Transcript`/`Rows`를 그대로 제공한다. 저널은 보존. — **완료** (cxz#240, cxz#242)
2. 서버의 `events` 캐시와 `lockProjection`의 재조정 제거. — **절반.** 저장소를 가진 세션은
   캐시를 쓰지도 채우지도 않는다. 코드는 남아 있다: 아직 변환되지 않은 세션과, 저널이 없는
   매니저가 그 경로를 쓴다. 4단계가 끝나면 지운다.
3. 프로젝트 볼륨 → 매니저 볼륨의 `projects/<id>/state` 서브패스. 매니저는 read-only.
4. 매니저의 `m.cache`·capture·폴백 제거.
5. 저널 쓰기 중단, 보존 기간 뒤 제거.

## 따로 지우지 않는 것

지금 폐기할 필요가 없는 것들이다. 단계가 진행되면 자리 자체가 없어진다.

- `transcript_format` 테이블 — `meta.rows_format` 행 하나가 대신한다.
- 워터마크 없는 투영을 입양하는 분기(cxz#213). 라이브에서 포맷 5인 세션 14개는 전부
  워터마크가 있지만, 포맷 5는 워터마크보다 **먼저** 들어왔으므로(`345e973` vs `7948f2c`)
  그 상태는 원리적으로 도달 가능하다. 죽은 코드가 아니라 일회성 지름길이므로 지금 지우지
  않는다. 세션당 DB에서는 워터마크가 처음부터 있으니 분기가 사라진다.
- 서버의 `events` 캐시와 `lockProjection`의 재조정 — 2단계.
- 매니저의 `m.cache`·capture·폴백 — 4단계.

## 결정된 것

- 백그라운드 워밍은 하지 않는다. 1단계가 그 비용을 없애므로 버려지는 작업이다.
- `rows`/`records`는 세션 DB에 같이 둔다.
- 검색 색인은 매니저에 하나로 두고, 커서 기반 pull로 바꾼다.
- 번호는 위의 `meta` 표대로. `rows_format`은 5를 이어받는다.
- 순서는 위의 단계 그대로. 2·3·4단계는 1단계 뒤에.

## 아직 결정되지 않은 것

- 저널을 얼마나 남길 것인가. 지금 계획은 4단계까지 얼린 채 두고 5단계에서 지우는 것인데,
  "4단계가 끝나고 며칠"인지 "한 릴리스 주기"인지는 정하지 않았다.
- 세션 DB가 `conversation.db` 하나인지, 첨부처럼 곁에 두는 것이 더 생기는지. 지금은 하나로
  충분해 보인다.
