# 대화 저장소: 세션이 자기 대화를 쓴다

상태: 제안. cxz#238. 구현은 이 문서가 합의된 뒤에.

목표는 하나다. **대화의 내구 저장소를 세션당 하나로 만들고, 그것을 쓰는 프로세스를 그
세션의 수퍼바이저 하나로 둔다.** 그러면 프로세스가 새로 뜰 때마다 저장소 둘을 맞추는
일이 사라지고, 매니저가 들고 있는 두 번째 사본도 사라진다.

## 지금의 지도

프로젝트 컨테이너 안에서 실제로 돌고 있는 것들이다.

```
cxz --state /cxz/state/data _project              서버.       프로젝트당 1개
cxz --state /cxz/state/data _supervise <session>  수퍼바이저.  세션당 1개
└─ codex app-server | claude                      에이전트.   수퍼바이저의 자식
   └─ cxz … _mcp-bridge <session> <name>
```

| | 수퍼바이저 (세션당) | 서버 (프로젝트당) |
|---|---|---|
| 쓰기 | 자기 세션의 `events.jsonl` | `cxz.db`: `events` 캐시, `transcript_*`, `sessions` |
| 읽기 | 자기 저널 | 모든 세션의 저널 |
| DB | 접근하지 않는다 (패키지에 참조가 없다) | `daemon.lock`을 잡은 단독 writer |
| 소켓 | 세션별 소켓 (`update-status`/`activity`/`stop`) | 프로젝트 gRPC 소켓 |

저장소마다 writer는 하나다. 저널은 세션별 파일이라서, DB는 `core.Lock(root/daemon.lock)`
이라서 그렇다. 나머지는 모두 읽기다 — `versionuse`는 `mode=ro`로 열고, 버전 전환 경로는
같은 `daemon.lock`을 잡아 서버가 없을 때만 진행한다. `conversations.db`(검색)와
`auxiliary`는 애초에 별도 파일이며, 그 이유가 `internal/convindex/index.go`에 적혀 있다:
단일 커넥션 뒤에 검색이 줄을 서지 않게 하려고.

## 무엇이 문제인가

내구 저장소가 **둘**이다. 저널과, 그것을 복사한 `cxz.db`의 `events`. 그래서 서버가 새로
뜨면 세션마다 저널을 처음부터 읽어 (a) 살아있는 스냅샷을 리플레이하고 (b) 캐시의 꼬리가
저널과 일치하는지 확인한다. `cxz` 프로젝트를 recreate한 직후 측정했다.

```
세션당 첫 접근 (디스크 캐시 따뜻한 상태, 라이브 DB 스냅샷 대상)
  4d683e9c  82MB/ 78,339  lockProjection 603ms  sync 153ms  page  39ms
  d57f2e00  85MB/122,236  lockProjection 946ms  sync 158ms  page 102ms
  9b3bc6ba  72MB/103,498  lockProjection 539ms  sync   0ms  page 104ms
  c99d1b14  47MB/ 32,904  lockProjection 260ms  sync   1ms  page  60ms

저널 읽기와 리플레이만 따로 재면
  read 453ms / replay 11ms,  413/6,  203/1,  529/19
```

비용은 거의 전부 읽기와 파싱이다. 리플레이는 6~19ms다. 그리고 그 작업은 세션별 projection
락을 쥐고 일어나므로, 같은 세션에 오는 다른 호출이 뒤에 선다. 라이브 로그가 그 모양이다.

```
Transcript        OK  3635ms  waited_ms=0     ← 락을 쥔 쪽
Background        OK  3072ms  waited_ms=3001  ← 뒤에서 대기
GetHistoryFloor  ×4  2000ms  Unknown         ← 2초 데드라인에 실패
List             ×2  ~2000ms Unknown
```

사용자에게는 "대화 불러오기가 느리다"로 보인다. 이것은 cxz#227에서 고친 두 가지와 성질이
다르다. 그 둘(버릴 본문을 읽던 metadata 쿼리 0.3~2.0초, 재시작마다의 체크포인트 재기록
3.98초)은 **버그**였고 고쳐졌다 — 지금 `Page`는 1~2ms, 재조정 없는 sync는 82ms다. 남은
이것은 **구조**다. 저장소가 둘이라서 생긴다.

매니저 쪽에 같은 중복이 한 겹 더 있다. 매니저는 프로젝트 컨테이너의 볼륨을 읽을 수 없으니
대화를 자기 `cxz.db`로 복사해 둔다 — `m.cache`, `down` 직전의 capture("history survives
the container"), 런타임이 답하지 않을 때의 폴백("remains readable offline"). 그 복사본
때문에 매니저 DB가 845MB다. 복사가 있는 이유는 정당하다: `project down`은 컨테이너만
지우고 데이터를 남기고, 지금 `xli`가 `absent` 상태로 그렇게 있다. 컨테이너가 없어도 대화는
읽혀야 한다.

## 설계

### 세션당 대화 DB 하나, writer는 그 세션의 수퍼바이저

```
sessions/<id>/conversation.db     세션당 1개. writer는 그 세션의 수퍼바이저 하나.
  meta                            스키마 버전
  events                          provider가 말한 것. 내구적.
  rows, records                   표시용 리덕션. append와 같은 트랜잭션.
  snapshot                        리덕션 상태 1행. 재시작이 이것을 읽는다.
```

수퍼바이저는 이미 리덕션을 하고 있다 — `snap`(state·run id·vendor id·last seq),
`pending`, `updateTools`, `updateBackground`를 append하는 자리에서 유지한다. 표시용 행
리덕션(`transcripthistory.Projection.Apply` + `summary()`)은 서버에 의존하지 않는 순수
함수이며, 이미 서버 밖에서 돌고 있다: WASM 샌드박스가 `memory.go`의 `FromEvents`로 같은
리덕션을 한다. 옮기는 것은 호출 주체다.

그러면 이렇게 된다.

- **재조정이 없다.** 복사할 것이 없고 행이 이미 거기 있다. 위의 0.3~1.2초가 0이 된다.
- **재시작이 리플레이가 아니다.** 스냅샷 한 행을 읽는다. 이 메커니즘은 이미 있다 —
  압축이 쓰는 `core.HistoryCheckpoint`가 `Snapshot`을 품고 `ReplayFrom`이 거기서 리셋한다.
  이 설계는 그것을 압축 때만이 아니라 평상시 경로로 만든다.
- **writer가 파일당 하나로 유지된다.** fork는 파일 복사, 압축은 행 삭제, purge는 unlink다.
  오늘 파일이 주던 격리가 그대로다.
- **서버와 매니저는 읽기만 한다.**

### 왜 리덕션을 버리지 않는가

"진실 하나만 읽자"가 자연스러운 질문이고, 답은 리덕션이 사본이 아니라 **해석**이기
때문이다. 행 하나가 이벤트 여럿의 축약이고, 나중 이벤트가 앞선 행을 고친다.

- 툴 호출 하나가 `tool_call` → `tool_output` → `tool_result` → `approval` →
  `approval_resolved`로 도착해 **행 하나**로 접힌다(`pending`→`working`→`completed`/`failed`).
- `turn_end`은 자기보다 **앞선** assistant 행에 토큰·비용·소요시간을 접어 붙인다. 둘은
  수천 이벤트 떨어져 있을 수 있다.
- `raw`·`state`·`vendor`·`usage` 같은 kind는 행을 만들지 않는다.
- 페이지가 작으려면 payload를 떼야 한다. 원문은 `EventDetails`로 필요할 때만.
- `updated` 열이 행 버전 스트림을 가능하게 한다. 정정이 뒤에 도착하고 읽는 쪽이 seq로
  교체한다.

그래서 매 페이지마다 리덕션을 다시 하려면 **얼마나 거슬러 올라가야 하는지 알 수 없는**
역방향 스캔을 해야 한다. 그 비용의 실측이 cxz#227에 있다: 1.6만~2.6만 레코드를 훑던
쿼리가 0.3~2.0초였다.

반대로 리덕션을 내구 저장소로 삼으면 — 행만 남기면 — **리덕션 버그가 영구 데이터
손실**이 된다. `projectionFormat`이 이미 5인 것이 해석이 네 번 바뀌었다는 뜻이다. 지금은
`toolview`를 고치고 다시 만들면 되지만, 행만 남기면 과거 대화가 틀린 모양으로 영원히
남는다. `EventDetails`의 원문 보기, fork, resume(vendor id·`checkpoint.Resume`)도 이벤트가
있어야 성립한다.

결론: **이벤트는 내구적으로 남고, 리덕션은 그 옆에 같은 트랜잭션으로 저장된다.** 파생이
사라지는 것이 아니라, 파생을 만드는 주체가 소유자와 같아지고 저장소가 하나가 된다.

세션을 넘는 파생만 따로 남는다 — 검색 색인(`conversations.db`)과 리소스 저장소
(`resources.db`). 세션 DB 안에 둘 수 없는 것들이고, 검색 색인이 파생인 것은 어느
설계에서도 그렇다.

### 규칙

**내구성.** 지금 `AppendBatch`는 배치마다 `l.f.Sync()`를 호출한다. 같은 보장을 유지하려면
WAL + `synchronous=FULL`로 커밋당 fsync다. 비용은 오늘과 같다(배치 단위).
`convindex`가 `NORMAL`인 것은 파생 데이터라서이며, 대화에는 쓰지 않는다.

**리덕션 실패가 append를 막지 않는다.** 지금은 이상한 payload에 리덕션이 넘어지면 *보기*가
깨지지만, 쓰기 경로로 들어오면 *기록*이 막힐 수 있다. provider가 예상 밖의 것을 보내는
일은 실제로 일어난다 — cxz#235의 `codex-code-mode-host`가 그런 식으로 왔다. 그래서:

> 이벤트를 먼저 커밋한다. 행은 같은 트랜잭션에서 최선으로 쓰되, 리덕션이 실패하면 그
> 세션에 "행 재구축 필요" 표시를 남기고 이벤트는 그대로 둔다.

**포맷 버전과 과거 행.** 재구축 주체는 그 세션의 수퍼바이저인데, 멈춘 세션에는
수퍼바이저가 없다. 지금 설치본의 세션 23개 중 13개가 `stopped`이므로 가정이 아니다.
선택지는 셋이고, 선호는 첫 번째다.

1. **읽는 쪽이 기록된 포맷 그대로 읽는다.** 행에 버전이 적혀 있으면 읽는 쪽이 "이건 v4
   행이다"를 알고 다룬다. 멈춘 대화는 더 이상 바뀌지 않으니 재구축이 필요 없다 —
   재구축 자체가 줄어든다.
2. 세션이 다음에 시작될 때 재구축한다. 멈춘 채로는 옛 모양으로 남는다.
3. 서버가 멈춘 세션에 한해 재구축한다. writer 하나 규칙에 예외를 만든다.

**스키마 스큐.** 세션 DB를 쓰는 것은 자기 수퍼바이저 하나뿐이므로, 필요한 것은 버전 열과
"내가 모르는 스키마면 쓰지 않는다"다 — 서버가 `user_version`에 적용하는 규칙과 같다.
수퍼바이저를 서버와 lockstep으로 올리는 방법도 있지만 공짜가 아니다. 업데이트가 계단식인
것은 턴 중인 세션을 끊지 않기 위해서이고, lockstep은 "프로젝트 런타임이 올라갈 때 세션
재시작" 또는 "모든 세션이 조용해질 때까지 서버 대기" 중 하나를 강요한다. 후자가 cxz#224와
cxz#235에서 업데이트를 멈춰 세운 그 게이트다.

## 2단계: 프로젝트별 볼륨 → 매니저가 소유한 디렉터리의 서브디렉터리

매니저 캐시를 없애려면 매니저가 세션 DB를 직접 읽어야 하고, 그러려면 프로젝트 상태가
도커 볼륨이 아니라 파일시스템 경로에 있어야 한다. **이 패턴은 이미 쓰이고 있다.** 지금
프로젝트 컨테이너의 마운트다.

```
bind …/cxz-…-state/_data/assets/exports/716fff60…  -> /cxz/assets   rw=false
bind /dev/shm/cxz-…/716fff60…                      -> /cxz/secrets  rw=true
volume cxz-dc4e87dca740-716fff60…-state            -> /cxz/state    rw=true   ← 바꾸려는 것
bind /home/somnus/workspaces/github.com/…/cxz      -> /workspace    rw=true
```

첨부와 시크릿이 이미 "매니저가 소유한 트리의 프로젝트별 서브디렉터리를 컨테이너에 바인드"
다. 새 메커니즘이 아니라 `/cxz/state`로의 확장이다.

조건은 둘이다.

- **매니저는 read-only다.** 쓰기까지 열면 롤아웃 중에 서로 다른 버전의 두 바이너리가 한
  DB에 쓴다. 어제 실제로 매니저는 `5bd4c0c`, 수퍼바이저는 `6f7ea45`였다.
- **Linux 호스트의 실제 파일시스템을 전제한다.** 서버 실행이 Linux 전용이므로 전제가
  성립한다. Docker Desktop의 바인드(virtiofs/gRPC-FUSE)에서는 SQLite 락을 신뢰할 수 없고,
  named volume이 지금 그 문제를 피하고 있다는 점만 기록해 둔다.

단일 writer·다중 reader는 WAL이 가장 잘 하는 모양이다. reader는 writer를 막지 않고 그
반대도 아니다.

## 마이그레이션

두 단계의 마이그레이션은 성질이 다르다.

**2단계(볼륨 → 디렉터리)는 바이트 복사다.** 데이터 모양이 바뀌지 않으므로 런타임을 멈추고
볼륨 내용을 새 디렉터리로 복사하면 끝이다. export/import 왕복으로 하면 저널 바이트·seq·
run id·첨부 하드링크를 재구성해야 하고, 조금이라도 빠뜨리면 그것이 히스토리 손실이다.

**1단계(저널 → 행)는 일회성 변환기다.** 수퍼바이저가 시작할 때 자기 세션의 `events.jsonl`을
읽어 `conversation.db`에 넣고, 끝나면 저널을 보존 모드로 남긴다(지우지 않는다). 변환이
끝난 세션은 DB를 진실로 읽고, 저널은 한동안 그대로 둬서 비교·복구에 쓴다.

범용 export/import는 **향후 기능**으로 둔다. 지금 cxz에서 대화를 밖으로 꺼내는 방법이
없다는 것은 그 자체로 메울 구멍이지만, 이 변경의 전제조건은 아니다.

## 버리는 것과 대체 수단

저널이 공짜로 주던 다섯 가지다.

| 저널이 주던 것 | 대체 |
|---|---|
| 서버와 무관한 쓰기 내구성 | 유지된다. 수퍼바이저가 자기 DB에 직접 쓴다 |
| fork = 접두부를 읽어 다시 쓰기 | 행 복사 + `session_id` 치환. 지금도 단순 복사가 아니라 `SessionID`를 바꾸고 vendor 식별자를 비운다 |
| 압축 = 파일 재작성 | 행 삭제 + `VACUUM`, 체크포인트는 `snapshot` 행 |
| 찢어진 꼬리를 노출하지 않음 | 트랜잭션 |
| 파일 변경이 곧 신호(`observeJournals`) | WAL 감시 또는 기존 폴링(cxz#213 이후 0.005ms) |
| 스키마 없음 → 버전 스큐 무해 | **대체 없음.** 버전 열 + "모르면 쓰지 않는다"가 비용이다 |

마지막 줄이 이 설계가 새로 들이는 유일한 불변식이다.

## 단계

1. 세션당 `conversation.db`와 변환기. 수퍼바이저가 쓰고, 서버는 그것을 읽어 지금의
   `Transcript`/`Rows`를 그대로 제공한다. 저널은 보존.
2. 서버의 `events` 캐시와 `lockProjection`의 재조정 제거.
3. 프로젝트 볼륨 → 매니저 소유 디렉터리의 서브디렉터리. 매니저는 read-only.
4. 매니저의 `m.cache`·capture·폴백 제거.
5. 저널 쓰기 중단, 보존 기간 뒤 제거.

- `rows`/`records`를 세션 DB에 같이 둘 것인가, 세션별 파생 DB를 따로 둘 것인가. 같은 DB면
  쓰기 락을 공유하지만 writer가 하나이므로 경합 상대가 없다 — 같이 두는 쪽이 단순하다.
- 검색 색인이 세션 DB들을 어떻게 따라갈 것인가. 지금은 매니저가 캐시를 쓸 때
  `extractConversation`으로 같이 갱신한다. 캐시가 사라지면 그 자리가 바뀐다.
- 오늘 체감되는 비용을 1단계 전에 백그라운드 워밍으로 먼저 없앨 것인가. 1단계가 그것을
  무의미하게 만들므로, 1단계가 임박하면 건너뛴다.
