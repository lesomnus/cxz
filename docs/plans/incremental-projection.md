# 투영: 점진적으로 읽기

상태: 구현됨. 싼 변화 감지는 cxz#213, 나머지 세 단계와 `count` 제거는 이 문서와 같은
갈래에서 구현됐다. 읽기 투영 자체의 설계는 `internal/transcripthistory/history.go`의 주석과
`internal/server/rows.go`를 참고한다.

목표는 하나다. **투영의 비용이 대화 길이가 아니라 바뀐 양에 비례하게 만든다.**

## 지금 무엇이 문제인가

살아있는 설치본에서 측정했다. 세션 하나의 프로젝트 런타임이 코어의 29%를 꾸준히
쓰고 있었고, 옆 프로젝트의 런타임은 0.08%였다.

```
_project (pid 108)   코어의 29%
rchar                33.5 MB/s      read syscall 8250/s      wchar 274 KB/s
pread64              12초에 80,210회, 98%가 cxz.db
읽기 추이            21~31 MB/s, 주기성 없음 → 티커가 아니라 상시 루프
cxz.db               869 MB, 최다 세션 레코드 134,495개
같은 질문, 옆 프로젝트  cxz.db 14 MB, 295 B/s
```

`Rows`는 열린 스트림마다 150ms 간격으로 `transcripthistory.Sync`를 부른다
(`internal/server/rows.go:52`). 그 폴링 한 번에 O(대화 전체)인 비용이 둘 있었다.

1. **변화 감지.** `SELECT COUNT(*),MIN(seq),MAX(seq) FROM events WHERE session_id=?`
   — 카운트는 훑는 것이고, 134,495 레코드에서 15ms(드라이버 경유 25ms)다. 150ms
   간격이니 스트림당 코어의 1/5을 "바뀐 게 없다"는 답에 썼다. cxz#213에서 싼 질문
   셋으로 바꿨다: `MAX(rowid)`, `MIN(seq)`, `MAX(seq)` 각 0.005ms.

2. **복원.** 뭔가 바뀌었으면 그 세션의 현재 행을 **전부** 읽어 메모리 투영을
   되살린다 (`history.go:490` 부근). 같은 세션에서 2,745행·16.4MB JSON·47ms이고,
   활성 대화 중에는 150ms마다 돈다. 이게 남은 비용의 지배적인 몫이다.

## 왜 전부 다시 읽는가

읽는 것이 둘인데 하나로 보였다.

- **새 레코드**는 이미 커서부터만 읽는다 — `WHERE seq > oldLast`. 증분이다.
- **리듀서의 메모리 상태**는 매번 전부다. `Sync`는 호출마다 `projection := New()`로
  빈 투영을 만들고 DB에서 상태를 되살린다.

행 축약이 레코드 하나만 보고 되는 연산이 아니기 때문이다. 선행 맥락이 필요하다.

| 상태 | 무엇인가 | 어디서 오는가 |
| --- | --- | --- |
| `questions` | 아직 열린 승인/질문 | 앞선 `approval` 행 |
| `tools` | 결과와 짝지을 도구 호출 | 앞선 `tool_call` 행 |
| `last` | run별 마지막 assistant 응답 | 앞선 `assistant` 행 |
| `input`, `inputSeq` | 현재 입력이 언제 시작됐는지 | 앞선 `input` 행 |

그런데 `Sync`는 호출 사이에 아무 상태도 보관하지 않는 함수다. 코드의 주석이 이미
한 단계 최적화한 흔적을 남겼다 — "Restoring the reduced tools/last responses avoids
walking old native bodies", 즉 원본 레코드를 다시 축약하는 것보다 축약된 행을 읽는
게 싸다는 것. 다음 단계는 **읽지 않는 것**이다.

## 이미 있는 것

새로 만들 것이 적다. 필요한 재료가 대부분 이미 있다.

- **연관 식별자.** `transcript_records(session_id, seq, run_id, request_id, kind,
  related_id)`에 인덱스 셋이 걸려 있다 (`history.go:386`). `request_id`는 에이전트가
  준 `tool_use_id`가 그대로 들어온 것이다 (`internal/supervisor/supervisor.go:687`).
  따로 trace id를 부여할 필요가 없다.
- **그 인덱스로 거슬러 올라가는 선례.** `EventDetails`는 행 하나 뒤의 레코드들을
  재생 없이 run+request/related로 바로 집어온다 (`history.go:771`).
- **맥락이 없을 때의 정의된 동작.** `tool_result`가 왔는데 호출을 본 적이 없으면
  결과만으로 행을 만든다 (`history.go:203`). 승인 경로도 짝이 없으면 건너간다
  (`history.go:245`, `:266`).
- **완전 복원은 애초에 보장이 아니다.** 트림은 `first`를 움직여 재구축을 유발하고,
  재구축은 남아 있는 것만 재생한다. 플로어 아래 레코드의 짝은 어떤 방법으로도 찾을
  수 없다. 지금의 전체 재생이 사주는 것은 시스템이 약속하지 않는 완전성이다.

읽기 경로도 이 상태를 필요로 하지 않는다. `Page`와 `Tail`은 `transcript_rows`를
직접 읽는다 (`history.go:615`, `:829`). 메모리 투영은 **새 레코드를 행으로 축약할
때만** 쓰인다.

## 설계

네 경로 각각의 비용을 바뀐 양에 비례하게 만든다.

| 경로 | 지금 | 목표 |
| --- | --- | --- |
| 변화 없음 | 카운트 15ms | 싼 질문 셋 0.015ms (cxz#213) |
| 변화 있음(웜) | 현재 행 전부 2,745행·16.4MB·47ms | 캐시 + 새 레코드만 → O(새 레코드) |
| 재시작·재구축(콜드) | 대화 전체 재생 | 열린 턴만 → O(한 턴) |
| 짝 누락 | 미리 다 적재해 방지 | 인덱스 조회 1회로 요청 시 해결 |

### 1단계 — 웜 경로: 투영을 들고 있는다 (cxz#213 이후)

주인은 이미 있다. `internal/server`의 `sessionProjection`이 세션별 mutex와 축약
상태(`background`, `catalogs`)를 들고 있고, `Rows` 폴링은 그 락 안에서 `Sync`를
부른다 (`rows.go:91`).

- `transcripthistory`에 `Cache`를 추가한다. 투영과 그것이 만들어진 DB 상태
  — `(first, last, format)` — 를 함께 들고 있는다.
- `Sync`는 그대로 두고(`nil` 캐시로 위임), `SyncWith(ctx, db, id, decode, *Cache)`를
  더한다. 캐시를 모르는 호출자는 동작이 바뀌지 않는다.
- 캐시가 DB 상태와 맞고 변화가 순수한 추가면 복원을 건너뛰고 새 레코드만 적용한다.
  어긋나면 캐시를 버리고 지금처럼 복원한다.
- 캐시는 `sessionProjection.mu`를 쥔 호출자만 넘긴다. 락 밖의 호출자는 `nil`을
  넘긴다 — 캐시에 자체 락을 더해 두 개의 락을 만들지 않는다.

### 2단계 — 콜드 경로: 열린 턴만 복원한다

재시작 직후나 재구축 뒤의 첫 호출은 캐시가 없다. 그때도 대화 전체를 재생하지 않는다.

- `transcript_metadata(session_id, kind, seq)`로 마지막 `turn_end`의 seq를 찾는다.
  그 뒤의 행만 복원한다 — 리듀서가 아직 필요로 할 수 있는 것은 닫히지 않은 턴에
  있다.
- 열린 승인은 지금처럼 전용 쿼리로 따로 가져온다 (`history.go:545`).
- 범위를 벗어난 짝은 3단계의 조회로 해결한다.

### 3단계 — 짝 누락: 필요할 때 거슬러 올라간다

백그라운드 작업의 결과는 자기 턴이 끝난 뒤에 올 수 있다. 그 호출은 열린 턴 범위
밖이다.

- 리듀서에 선택적 resolver를 준다. `tools[key]`가 비었을 때 `(run_id, request_id)`로
  행을 한 번 찾는다.
- `transcript_execution` 인덱스로 seq를 찾고 `transcript_rows`에서 그 행의 최신
  버전을 읽는다. `EventDetails`(`history.go:771`)와 같은 모양이다.
- 못 찾으면 지금의 동작 그대로 — 결과만으로 행을 만든다. 플로어 아래는 그 길뿐이다.

### 4단계 — `count` 제거 (cxz#213의 연장)

`count != oldCount+suffix`가 답하는 질문은 "커서 뒤에 뭔가 생겼나"다. 삽입 순서로
물으면 싸다.

```sql
SELECT EXISTS(SELECT 1 FROM events NOT INDEXED WHERE rowid>?seen AND session_id=? AND seq<=?cursor)
```

새로 들어온 행만 훑으므로 O(새 행)이다. `NOT INDEXED`가 필요하다 — rowid 범위가
여기서 원하는 인덱스인데, 없으면 SQLite가 `(session_id,seq)`를 골라 그것을 훑는다.
134,495 레코드 세션에서 9.8ms 대 0.005ms로, 바로 이 질문이 없애려던 비용이다.
워터마크가 없는 투영(이 변경 전에 만들어진 것)은 비교 대상이 없으므로 묻지 않고
테이블의 표식을 채택한다. 세션마다 한 번씩 재구축하지 않기 위해서다. 앞쪽 트림은 `MIN(seq)`가 잡는다 — 삭제는
rowid를 쓰지 않기 때문에 끝점을 함께 묻는다. 그러면 `transcript_state.count`는 쓰이지
않게 되고, 옆 세션의 쓰기가 이 세션에 검증 한 번을 물리던 교차 비용도 사라진다.

## 지켜야 할 것

- **rowid 재사용.** SQLite는 `max(rowid)+1`을 주고 max 아래 빈 자리는 재사용하지
  않는다. 재사용되는 경우는 **최댓값 행이 지워졌을 때 그 값** 하나뿐이다(그리고
  2^63-1에 도달하면 임의 값). 그래서 워터마크는 `>`가 아니라 **등호**로 비교한다 —
  max가 내려가도 검증이 돌게. 두 폴링 사이에 최댓값이 지워지고 같은 rowid로 다시
  삽입되는 조합만 놓치는데, 그건 지금의 카운트 검사도 놓친다.
- **캐시 무효화.** 캐시는 자신이 만들어진 `(first, last, format)`을 들고 있고, DB가
  말하는 값과 다르면 스스로를 버린다. 다른 프로세스가 같은 DB의 투영을 재구축해도
  이 비교에서 걸린다.
- **상주 메모리.** 지금은 폴링마다 2,745행·16MB를 만들었다 버린다. 캐시를 열린 턴
  범위로 한정하면 상주 메모리가 대화 길이에 비례하지 않는다. `put`/`Apply`가
  `Rows`를 어디까지 거슬러 참조하는지는 2단계에서 확정한다 — 턴 지표를 이전 응답
  행에 접어 다시 발행하는 경로가 같은 턴 안인지를 본다.

## 어떻게 확인할 것인가

성능은 단정할 수 있을 때만 고쳤다고 말한다.

- 테스트는 비용을 직접 센다. `counted`는 레코드를 훑은 횟수다(cxz#213). 같은 방식으로
  복원 횟수와 복원한 행 수를 센다. "다섯 번 더 봐도 0회", "추가는 정확히 1회",
  "콜드 복원은 한 턴 이하"를 단정한다.
- 살아있는 설치본은 이렇게 재측정한다.

  ```sh
  # 프로세스 CPU와 읽기량
  grep ^rchar /proc/<pid>/io          # 5초 간격 두 번
  sudo strace -f -c -p <pid>          # pread64 호출 수
  # 어느 파일인지
  sudo strace -f -e trace=pread64 -p <pid> | grep -oE 'pread64\([0-9]+'
  ```

  cxz#211의 `cxz diag stats`가 배포되면 `Rows` 스트림의 p50/p99로도 보인다.
