# v0.1.5

리소스 API 재설계 릴리즈입니다. 명령 하나가 JSON 덩어리로 열두 가지 일을 나르던 `Project.Docker` 봉투를 비웠고, 그 과정에서 v0.1.4에 들어 있던 버그 하나를 찾아 고쳤습니다.

**CLI는 하나도 바뀌지 않았습니다.** `docs/cli.md`에 변경이 없습니다. `cxz mcp`, `cxz skill`, `cxz docker`, `cxz devcontainer`, `cxz session purge`를 쓰던 방식은 그대로입니다.

## 업그레이드

```sh
cxz use v0.1.5      # 또는 cxz use @stable
```

상태 스키마는 v0.1.3·v0.1.4와 같은 2이고 프로토콜도 1이라, v0.1.4에서는 자동 업데이트로도 올라옵니다.

### 올라오는 동안의 혼합 버전

교체는 원자적이지 않습니다. Manager는 설치의 모든 세션이 idle일 때, 프로젝트 Runtime은 그 프로젝트의 세션이 idle일 때, TUI는 5분간 입력이 없을 때 각각 교체됩니다. 그 사이에는 버전이 섞입니다.

**대화는 영향을 받지 않습니다.** 없어진 호출은 `Project.Docker` 하나이고, 입력·응답·승인·이력은 그 호출을 쓰지 않습니다.

영향을 받는 것은 설정 화면입니다. 한쪽이 상대가 모르는 호출을 하면 `Status unavailable: ... / Update the host manager if this operation is unavailable.`로 알리고 그 화면만 비활성화됩니다. 매니저가 프로젝트 Runtime에 보내는 설정 푸시(스킬·MCP·보존 한도)는 `Unimplemented`를 "아직 모르는 런타임"으로 받아들이고 넘어가므로, **런타임이 설정 하나를 몰라서 프로젝트 전체가 멈추는 일은 없습니다.** 양쪽이 같은 빌드가 되면 알아서 풀립니다.

## 고친 것: 사라진 히스토리를 계속 내주던 캐시

v0.1.4에 들어 있던 버그입니다. 매니저는 프로젝트 런타임에 "저널을 어디까지 잘라냈는지" 물어서, 자기 캐시가 **저널에 더 이상 없는 히스토리를 내주지 않도록** 합니다. 그 질문이 닿지 않고 있었습니다.

v0.1.4에 들어간 변경에서 그 호출을 "런타임 전용"이라고 잘못 분류했는데, 매니저가 프로젝트 컨테이너에 닿는 경로가 바로 리소스 API입니다. 호출자는 옛 봉투를 그대로 쓰고 있었고 컨테이너는 같은 커밋에서 그 처리를 잃었습니다. 읽기에 실패해도 히스토리 조회 자체는 깨지지 않도록 에러를 삼키는 것이 의도된 설계라서 **증상이 조용했습니다** — 보존 한도로 지워진 턴이 캐시에서 계속 보였습니다.

이제 `SessionService.GetHistoryFloor`이고, 핸들러가 아니라 경로 전체를 고정하는 테스트가 붙어 있습니다. 보존 한도를 켜 둔 설치라면 이 릴리즈로 올라온 뒤 오래된 턴이 정리된 것으로 보일 수 있습니다 — 그게 원래 보여야 했던 상태입니다.

## 봉투를 비웠습니다

`Project.Docker{action, spec}`는 proto 메시지를 못 받은 모든 것의 봉투였습니다. RPC 하나가 32개가 되었습니다.

| 들어 있던 것 | 지금 |
|---|---|
| `secret-file` | `PutSecretFile` / `DeleteSecretFile` |
| `session-purge` | `SessionService.Purge` |
| `history-policy` · `history-floor` · `history-checkpoint-ready` | `Get`/`SetHistoryPolicy` · `GetHistoryFloor` · `MarkHistoryTrimmable` |
| `skills` (6개 동작) · `skills-sync` · `devcontainer-render` | `GetSkills` · `AddSkill` · `RemoveSkill` · `SetSkillDefault` · `SetProjectSkill` · `ClearProjectSkill` · `SyncSkills` · `RenderDevcontainer` |
| `mcp` (6개 동작) · `mcp-sync` · `mcp-state` · `mcp-control` | `GetMcpServers` · `PutMcpServer` · `RemoveMcpServer` · `SetMcpServerDefault` · `SetProjectMcpServer` · `ClearProjectMcpServer` · `SyncMcpServers` · `McpSessions` · `SessionService.McpLogs` · `RestartMcp` |
| `info` · `save` · `up` · `down` · `prune` · `status` | `GetEngineInfo` · `GetInstallationVersion` · `SaveEngine` · `StartEngine` · `StopEngine` · `PruneEngine` · `EngineStatus` |

그래서 달라진 것들:

- **라우팅이 payload를 읽지 않습니다.** 여러 설치에 붙은 클라이언트는 MCP 요청을 JSON으로 파싱해서 어느 연결의 호출인지 알아낸 뒤, 접두사를 떼고 다시 직렬화했습니다. 지금은 필드를 읽습니다.
- **권한이 메서드 단위입니다.** 프로젝트 안에서 구동되지 못하게 막던 검사가 핸들러가 기억해야 하는 문장이 아니라 메서드의 검사가 되었습니다.
- **비밀을 나르는 호출이 비밀을 나르는 이름을 갖습니다.** 삭제는 실수로라도 비밀을 실을 수 없습니다 — 그게 타입의 성질이 되었습니다.
- **결정을 섞을 수 없습니다.** 기본값을 켜는 것과 한 프로젝트에만 켜는 것은 다른 곳에 쓰는 다른 결정인데, 봉투는 필드가 비었는지로 구별했습니다. 이제 `SetSkillDefault`에는 프로젝트를 적을 곳이 없고, `ClearProjectSkill`에는 on/off를 적을 곳이 없습니다.
- **세션의 것이 세션 서비스에 있습니다.** MCP 로그와 재연결은 프로젝트와 세션을 함께 받아 서로 맞지 않는 짝을 거부해야 했습니다. 세션은 자기 연결을 가리키므로 짝 자체가 없어졌습니다.
- **설정 목록이 컨테이너를 기다리지 않습니다.** MCP 등록 목록을 읽는 것과 실행 중인 세션이 무엇으로 launch했는지 읽는 것이 다른 호출이 되었습니다. 멀쩡한 목록 끝에 `Runtime status unavailable.`이 붙는 일이 없습니다.
- **Docker를 묻는 질문이 cxz를 답하지 않습니다.** `info` 하나가 엔진 정보·보존 한도·cxz 버전을 함께 답했습니다. 버전을 읽으려고 엔진 락을 기다리던 것도 없어졌습니다.

열린 집합이 필요하지 않은 곳에는 enum을 썼습니다 — 엔진 모드 두 개, MCP 종류 세 개. 동작을 enum으로 만드는 것은 하지 않았습니다. 다섯 값 중 둘만 의미를 가질 수 있는 `spec` 필드는 봉투와 같은 결함이기 때문입니다.

설계 노트는 [docs/plans/aux-api.md](https://github.com/lesomnus/cxz/blob/v0.1.5/docs/plans/aux-api.md)이고, 진행 기록은 [#132](https://github.com/lesomnus/cxz/issues/132)입니다. 같은 모양이 하나 남아 있습니다([#143](https://github.com/lesomnus/cxz/issues/143)).

## 되돌아가기

v0.1.4가 이 재설계 **직전**의 빌드입니다.

```sh
cxz use v0.1.4
```

자동 업데이트는 되돌리지 않습니다. 설치된 리비전이 새 릴리즈의 조상일 때만 적용하므로, v0.1.5에서 v0.1.4는 다운그레이드로 판단되어 거부됩니다.
